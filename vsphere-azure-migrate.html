vSphere Center Installation to Azure Migrate Guide

Author: Infrastructure Systems Engineering · Target environment: on-premises OT engineering lab to Microsoft Azure public cloud · Confidential – Engineering test lab documentation

1. vCenter Server Stage 1 & Stage 2 Deployment

Deploying the VMware vCenter Server Appliance (VCSA) 8.0 under a tight resource environment requires specific host and network alignments to prevent identity broker crashes (VAMI crashes).

Core prerequisites & memory balancing

  • RAM requirements: The "Tiny" VCSA 8.0 deployment footprint strictly requires 14 GB of dedicated RAM to initialize core Linux back-end daemons.
  • Resource reclamation: Temporarily shut down surrounding heavy non-critical virtual machines (e.g., OT_SIEM, OT_KALI, Windows Server) to clear up at least 25 GB of host memory allocation space before initiating setup.

Network parameter maps

During Stage 1 network configuration, fill in the network settings exactly as follows to prevent loops:

ParameterTarget configuration value
System name (FQDN)vcenter.vsphere.local
Static IP address10.0.0.200
Subnet mask / prefix255.255.255.0 (or prefix: 24)
Default gateway10.0.0.1
DNS server lookup10.0.0.150 (points directly to ESXi host loopback helper)

Stage 2 Single Sign-On (SSO)

  • SSO domain: Maintain the default deployment identity vsphere.local.
  • SSO username: administrator@vsphere.local
  • Password complexity: Must contain uppercase, lowercase, numbers, and a supported non-parsing special symbol (e.g., use '!' or '*' instead of '$').

2. vCenter Client Datacenter & Host Mapping

Once the VCSA deployment reaches 100%, navigate to the primary vSphere dashboard at https://10.0.0.200 to map the localized physical layer assets.

  1. Log into the web portal using your SSO administrative context: administrator@vsphere.local.
  2. Right-click the root vCenter object entity and select New Datacenter. Define the cluster label (e.g., OTCyber-Datacenter).
  3. Right-click the new Datacenter container and select Add Host. Enter the physical asset IP: 10.0.0.150.
  4. Input the host administration root user account (root) and password, bypass the SSL fingerprint warning alert, and click Finish.

This maps your operational environment inventory tree (including OT_SCADA, OT_SIEM, OT_PLC, OT_KALI) instantly under central management control.

3. Windows Server 2019 Azure Migrate Appliance Configuration

To connect your vSphere cluster directly to your cloud landing zone using your available Azure credits, configure your existing Windows Server 2019 instance as an agentless migration bridge tool.

Appliance script implementation

  1. Log into the Azure Portal and open your migration workspace project OTCYBER2026.
  2. Generate a fresh project synchronization key. Copy the string token.
  3. Select the 500 MB script package deployment option (.ZIP format) and drop the archive directly onto your Windows Server 2019 workspace directory.
  4. Extract the contents, right-click AzureMigrateInstaller.ps1, and choose Run with PowerShell. Select options sequentially: Scenario: 1 (VMware vSphere) · Cloud: 1 (Azure Public) · Mode: 1 (Primary Appliance) · Endpoint: 1 (Public Endpoint)

VDDK local library placement

Azure Migrate explicitly validates the presence of the VMware Virtual Disk Development Kit library stream to pull snapshot blocks dynamically.

  1. Extract your downloaded VMware-vix-disklib-8.0.2 components.
  2. Manually construct this directory absolute path if it is not present: C:\Program Files\VMware\VMware Virtual Disk Development Kit
  3. Copy all binary and structural assets from inside the vmware-vix-disklib-distrib folder directly into that newly generated directory space.

Discovery & baseline optimization

Open https://localhost:44368 inside the server's browser. Paste the project cloud connection token key and type in your newly built local server details:

  • vCenter target endpoint IP: 10.0.0.200
  • Authentication mapping: administrator@vsphere.local

Once validated, click Start Discovery. To maximize your remaining cloud resource credits before expiration, configure a Performance-based Azure VM Assessment. Reduce predicted runtime parameters from 31 days/24 hours down to realistic testing lab windows (e.g., 15 days/8 hours daily) and deselect non-production management VMs to eliminate background credit run rates entirely.
